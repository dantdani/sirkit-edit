## 2. Registry rules for view-session tools (CONFIRMED)

`tool-registry.ts`: `TOOL_PROJECT_STATES` += `pcb-surface | pcb3d-surface | schematic-surface | workspace-surface`; `TOOL_BINDING_STATUSES` += `bound-view-session`; `ToolDescriptor.viewCommands`; `MUTATION_CLASSES` no longer lists `view-session` (it can never touch engineering state) but a view-session tool is a bus-command tool or nothing: `bound-view-session` binding, `session-state` side effects, authority `none`, approval tier `none`, a non-empty `viewCommands` list of `<editor>.<name>` ids, never an `*.observe` (the editor's own human-only mirror); a non-view tool may not list view commands. `validateToolDescriptor` refuses each violation (tested).

## 3. The view-command path: server-validated, browser-executed (CONFIRMED)

- **Capture** (browser): `app/lib/agent/view-session-bridge.ts` — every live editor view session registers (`useViewSessionBridge`: pcb3d and pcb in `PcbEditor` while a real board is loaded and never in demo mode; schematic in `SchematicEditor`; workspace on the page). `capture(projectTimeline)` builds ONE bounded `sirkit.view-context.v1` (surfaces, each editor's session id / view revision / bounded state — long arrays become counts, strings cut at 200, depth 6 — and the project operation timeline, ≤ 50 entries). The page sends it as the top-level `viewContext` body key of `/api/chat` (allowed keys now also `viewContext`; the B10 `editorContext` contract is untouched).
- **Assembly** (server): `assembleAgentRunContext({ view })` exact-key validates and bounds it (`validateCapturedViewContext`); malformed ⇒ withheld with a warning, no surface advertised, no view tool. Valid ⇒ `<editor>-surface` project states, `context.view` + `viewDigest`, the two sealed resources (`view-state-snapshot`, `project-timeline-snapshot`), and `maxToolCount = max(16, intentional.length + 4)` — derived, never a constant.
- **Integrity**: `verifyAgentContextIntegrity` recomputes the view digest and requires the advertised `*-surface` states to equal exactly the captured surfaces (a widened list or a dangling digest fails every invocation closed — tested).
- **Gateway**: a view-session call → fresh discovery (surface, role, capability) → role/capability recheck against the effective actor → `prepareViewCommandRequest`: the flat strict-schema arguments map onto ONE registered bus command (`viewCommandFor`, targets converted by `toolTarget`/`toolRefs`), the command must be in the descriptor's `viewCommands`, the surface must be captured, PCB/3D commands need the verified board, the command's own role gate and exact payload validation run against the SAME descriptors the browser bus runs (`serverViewCommands`), selection-relative targets are pinned to the captured selection digest, and "focus the selection" in 3D takes the PCB editor's captured refs. Output: `{ kind: "view-command", request }` — `sirkit.view-command-request.v1` with the editor, session id, command id, payload, `expectedViewRevision` (the captured revision), the agent actor, issue/expiry stamps, request id `vcr-<digest>`.
- **Loop**: outcome `view-command` → `tool_finished` status `view_command_dispatched` + event `view_command_ready { request }`; the model receives only "dispatched" plus the note that the editor may refuse a stale request and that the design is untouched. Trace class `view_command`.
- **Execute** (browser): `bridge.execute(request)` — exact parse (`parseViewCommandRequest`: agent actor only, no `observe`, command id prefixed by its editor), unexpired, live surface, the SAME session id, then `createViewCommand` with the request id as the invocation id (the bus's single settlement returns the settled result on a replayed event instead of running twice) and the bus's own stale-revision rule / role gate decide. The page shows "View updated — <command>" or the refusal in the activity log.
- **Fixture-only diagnostic hook** (RECORDED): when the server rendered the fixture-runtime banner (impossible in production — the fixture runtime refuses there), the page exposes `window.__sirkitViewBridge = { capture, execute }` bound to the same timeline and the same execute path so the deterministic browser journey can drive it exactly as a `view_command_ready` event would. It grants nothing: the bus rules decide.

## 4. Layout proposals: the shared candidate (CONFIRMED)

`app/lib/agent/layout-proposals.ts` — `LayoutProposalService`: exact allowlisted descriptor, fresh discovery, role AND capability recheck, verified canonical board, strict argument keys (authority-shaped keys `apply`, `commit`, `generation`, `expectedRevision`, … refuse by name), then `runPlacementCandidate` (B17-E; the ONE options builder; `timeoutMs` bounded by the tool deadline) or `runRoutingCandidate` (`app/lib/pcb/candidates/routing-server.ts`: `completeAutoroute` over an injected pass executor + `produceRoutingCandidate`, copper restricted to the requested nets). The FreeRouting pass executor was **extracted verbatim** from the autoroute route into `app/lib/pcb/autoroute/freerouting-pass-executor.ts` (`createFreeroutingPassExecutor`) and the route now calls it — the agent's routing proposal and the editor's autoroute run the identical passes; `/api/chat` wires it with the request signal and the tool deadline; an unavailable runtime refuses `routing_engine_unavailable`. Outcome `layout-candidate` → event `layout_candidate_ready { candidate }`; the page's SAFE receiver (`app/lib/project/layout-candidate-events.ts`: schema, kind, producer `agent`, digest intact) hands it to `PcbEditor`, which re-verifies base revision / expiry (`verifyLayoutCandidate`) and registers it in the SAME `LayoutCandidateStore` the editor's own runs use — the placement panel lists it, the routing panel shows the latest store candidate with the cyan ghost, Apply/Discard go through `autoPlace.apply(candidateId)` / `autoroute.apply(candidateId)` (B17-E's one canonical transaction). The proposal single-flight (one artifact per run) is unchanged. Long-running proposals (`budgetClass: long-running`) may use their registered timeout up to the remaining run deadline (the run boundary stays hard).

## 8. Unknowns and limitations (RECORDED)

- **UNKNOWN — live provider run.** No fixture agent provider exists and real LLM credits are unknown, so a real chat turn that calls these tools was not exercised end to end. The server half is proven through the SAME gateway/loop the route uses (scripted adapter), the browser half through the SAME bridge capture/execute the page's event handler uses; the route's `viewContext` key and event handling are INFERRED from the code path.
- The `pcb3d` surface exists whenever a real board is loaded in the PCB editor (the 3D sheet being closed is a state; `open` is a command). Without a board there is no pcb/pcb3d surface.
- `view.read-state` / `history-inspect` ride the canonical read boundary and therefore need a verified board even though the timeline is project-level.
- `selectedKinds` in discovery still come from the B10 editor-context selection (verified against the board), not from the view snapshot.
- One layout candidate per run (the proposal single-flight); the agent cannot apply, discard, undo or route to the router's debug bundle.
- The fixture-only `window.__sirkitViewBridge` hook exists only under the fixture runtime.
