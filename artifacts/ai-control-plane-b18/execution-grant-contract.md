Implemented in eight increments (`048b792` contract, `0a24e6d` explicit-request proof, `aa40756` store, `041939e` seal/mint/consume/settle, `08514ac` routes, `d33b255` agent contracts/loop/chat root, `ada258d` browser half, this closeout).

## 1. What a grant is (CONFIRMED — `app/lib/engineering/execution-grant.ts`, `b18-b-execution-grant.test.ts` 4/4)

`sirkit.agent-execution-grant.v1` — a server-owned durable record `{ grantId xg-<32 hex>, nonce (server-only), binding, identityKey, grantDigest, state }` whose **binding** pins: the verified principal + membership revision + role + session identity (`authorization`), the validated tenant/project/branch + board instance (`scope`), the editor + lineage + run (`session`), the provider/call/tool/registry/prompt (`origin`), the family / Tier 1 / grantable capability / decision / human-approval flag / autonomy snapshot (`operation`), the exact object targets and their digest (`targets`), the base (canonical revision digest; PCB semantic revision, board digest, history head, lineage, sealed validation policy) (`base`), the operations INSIDE the digest-covered binding with their digest, the human-readable preview and its digest and the **expected PCB revision after** (`proposal`), the instruction digest/excerpt and the explicit-request proof (`instruction`), issue/expiry/TTL.

- Digests: `operationsDigest` ignores minted operation ids and object versions; `identityKey` ignores the nonce and the session identity (the cross-session identity of the same intent); `grantDigest = digest(nonce, binding)` — the browser can echo it but cannot forge it (the nonce never leaves the server); the public projection strips the nonce and the session identity (D18-10).
- Families: the registry-`reversible` Tier 1 commands only (`pcb.move-footprint`, `pcb.rotate-side-footprint`, `pcb.arrange`, `pcb.silkscreen-text`, `schematic.set-property`, `schematic.move-rotate`); grantable capability `edit_placement` — a GRANT property, never granted to the agent actor (D18-8); family ⇄ kind ⇄ tier enforced at seal, consume and ritual (D18-7).
- Decisions (D18-4): `preview_then_confirm` (TTL 10 min, `requiresHumanApproval`) and `execute_explicit` (TTL 60 s); commit window 60 s + settle grace 60 s; attempt ids `eng1-…` from (identityKey, preparedAt, attempt nonce); the commitment from (identityKey, grantId, attemptId, run, preparedAt, authorization).
- State machine (monotonic, every transition one durable commit): `issued → consumed → settled | retired`; an issued grant retires with a closed vocabulary of 23 reasons (expired, superseded_by_new_grant, cancelled_by_user, session_changed, membership_changed, role_changed, scope_changed, confirmation_missing, proposal_altered, autonomy_changed, tier_exceeded, kind_not_allowed, revision_drift, history_drift, lineage_drift, selection_stale, run_cancelled, run_unsettled, …); a consumed grant retires only `consumed_unsettled` (lazy, after the commit window + grace) and still accepts a truthful LATE `committed` settlement.

## 2. Minting (CONFIRMED — `app/lib/agent/execution-intents.ts`, `app/lib/execution-grant/mint.ts`, `b18-b-mint-consume-decisions.test.ts` 7/7)

- The **pure seal** (agent layer, no authority): a canonical mutation binding whose command is an execution family of Tier 1, a permitted role, a grantable capability, a verified board with a PCB history basis, strict `{ moves }` arguments (authority-shaped keys `approval|grant|grantId|nonce|attemptId|capability|explicit|…` refused BY NAME), operations compiled through the SAME builder the browser recompiles with, kinds inside the family's kernel binding → data only (`AgentExecutionPlan`).
- The **only minter** (D18-3): built by the `/api/chat` composition root from the trusted request context and injected into the gateway and the loop as a closure (`AgentExecutionGrantMinter`); the agent layer never sees the instruction, the nonce or the store (import gates: `b18-b-import-gates.test.ts`). Inside: the explicit-request proof, the B18-A decision (`decideAgentExecution`), the cross-run retry guard (an identical instruction that COMMITTED or is in flight within 5 min re-issues as preview + confirmation), ONE durable commit that also supersedes the principal's earlier live grant of that editor. Storage unavailable ⇒ nothing is minted, not even a preview.
- The **explicit-request proof** (D18-5, `app/lib/engineering/explicit-request.ts`, `b18-b-explicit-request.test.ts` 4/4): the reference grammar (v1.0.0, `pcb.move-footprint`) parses the WHOLE user instruction, derives the operations against the verified board through the shared builder and proves explicitness only by a byte-equal operations digest; negation, questions, conditions, second clauses, pronouns, vague magnitudes, pasted text, injection, supersets, wrong direction/sign/axis/target are all UNPROVEN (preview + confirmation) — never execution. Coverage of the other five families' grammars is an owner decision (OD-11).

## 3. Storage (CONFIRMED — `app/lib/execution-grant/store.ts`, `b18-b-store.test.ts` 5/5)

Durable-workflow aggregates (D18-1: no new table/migration): `agent.execution-grant.v1` per grant (the full record incl. nonce — server-only) and `agent.execution-grant-index.v1` per (principal, editor) `{ live, recent ≤ 32 (with status + settlement outcome) }`; mint = one commit (grant rev 0 → 1, index CAS, supersession of earlier issued grants); consume / settle / retire = compare-and-set transitions with idempotent replays; lazy expiry of issued and consumed grants is itself a durable transition; every load re-verifies the record digest AND the grant digest (`EXECUTION_GRANT_RECORD_MISMATCH`); one outbox audit event per transition (`agent.execution-grant-issued | -consumed | -settled | -retired`) carrying ids, digests, principal, family, decision, reason, transaction — never the nonce or the operations. Idempotency keys: `grant-mint:<run>:<call>`, consume/settle/retire by grant + attempt/reason/revision.

## 4. Consumption and settlement (CONFIRMED — `consume.ts`, `settle.ts`, the routes; `b18-b-execution-grant-route.test.ts` 6/6)

`POST /api/agent/execution-grant` (tender | cancel) and `POST /api/agent/execution-grant/settle`, `GET /api/agent/execution-grant?grantId=` — canonical wrappers, policy rows `TIER1_EXECUTE = pcb_editor | project_admin` (read GET; mutate POST + POST /settle with same-origin CSRF; no `requiredCapability`; never a release row); classification durable read-write (the grant route `session-identity`); action record `agent.execution-grant`; the route-count ratchet moved 155 → **158 = 155 canonical + 3 factories + 0 raw** in the two literal pins; the classification/policy/coverage/B01/b16-0-4/7 artifacts regenerated (20 rows added). `/api/chat` is now truthfully durable **read-write** (it mints grants); its policy row stays `authenticated-propose` (OD-12).

The §4.2 checks run in order: forged handles (unknown id, wrong digest, another principal) are 404 with ZERO writes — the forgery checks run on the RAW head (`store.peek`), so not even the lazy expiry of an overdue grant is written for a forged handle — and the read is never an existence oracle; consumption has its own expiry gate independent of the lazy write (which retries once when its compare-and-set loses to a sibling grant's transition); a burn that loses its compare-and-set answers from the head; replays answer idempotently per attempt; every later failure burns the ISSUED grant with its exact reason — non-human actor, session change, membership change (through the B14 `evaluateMembershipReauthorization`), role change, missing confirmation of the exact preview, altered operations/preview digest, withdrawn autonomy, re-tiered family, kernel kind, revision / history / lineage drift, stale selection; the success path is ONE `issued → consumed` commit carrying attempt, commit deadline, the browser's commitment and the LIVE membership snapshot. Settlement is `browser-attested` and bound to the consumed attempt AND commitment; a committed settlement must name the transaction and the revision after; ANY truthful late report (committed, not-committed, poisoned) after the lazy `consumed_unsettled` retirement is recorded `late: true` — "outcome unknown" is never the final word when the browser knows. A replayed mint (the same run + call) answers with the grant the first commit minted.

## 5. The agent wire (CONFIRMED — `contracts.ts`, `loop.ts`, `trace.ts`, `route.ts`; `b18-b-loop-execution.test.ts` 6/6, `b18-b-chat-authority-keys.test.ts` 1/1)

- Outcome `execution-grant`, events `execution_grant_ready` and `execution_settled`, trace class `execution_grant` (grant id + operations digest in the proposal slots), budget `executionSettlementTimeoutMs` 60 s.
- The grant is the run's ONE side-effecting artifact (`proposal_exists` / `execution_exists` both ways). An `execute_explicit` grant makes the loop await the DURABLE settlement (bounded by the settlement budget and the remaining run deadline, raced against the run boundary) and answer the model `executed` (transaction, revision after, undo eligibility, DRC) / `execution_not_committed` (nothing changed) / **`execution_poisoned`** (a transaction LANDED but could not be verified: the board may have changed — never "nothing changed") / `execution_retired` / `execution_unsettled` — never from the browser directly. An untendered explicit grant is retired `run_unsettled`; a run that ends without completing retires its still-issued explicit grants `run_cancelled` (not gated on a consumed outcome — a mint discarded by the run boundary is retired too); preview grants outlive the run for the human.
- `/api/chat` refuses `executionGrant | grant | grantId | nonce | attemptId | consumption | explicit | explicitUserRequest | autonomy | decision | tier` BY NAME at every level its body grammar exposes (top level, each message, `scope`, `editorContext` and its `scope` / `selection`); `viewContext` is validated by the view-context assembler (exact keys, bounded) and never reaches a grant.
- The gateway carries the `executionGrants` seam only: the dispatch branch that seals a mutation intent and mints lands with the exposure lift (B18-C); every mutation class stays `not_callable` on this tree (the B04 invariant is untouched: `b18-b-loop-execution` drives the loop with a gateway double).

## 6. The browser ritual (CONFIRMED for the library half — `granted-executions.ts`, `agent-execution-journal(-idb).ts`, `execution-grant-client.ts`, `granted-execution-controller.internal.ts`; `b18-b-granted-executions.test.ts` 9/9 over the REAL composition. INFERRED for the composition wiring — `GrantedExecutionDialog.tsx`, `PcbEditor`, `page.tsx` — until B18-E's browser scenarios exercise it)

The B15.3 order re-derived for grants (D18-9): capture by bounded round trip + re-derived digests → expiry → live authority (current lifecycle, interlock, scope, canonical session) → in-memory claim → journal + canonical evidence disposition FIRST → live currency (revision, head, lineage, validation policy, selection; drift cancels the grant durably) → RECOMPILE through the shared builder with byte-match and kernel-kind check → durable PREPARE (`sirkit.agent-execution-journal.v1`: attempt nonce → attempt id → commitment, the bounded public grant kept for recovery) → CONSUME (one-shot server burn; a refusal changes nothing and abandons the entry) → grant-consumed → commit lease → EXACTLY ONE canonical transaction (`idempotencyKey = grantId`, `provenanceCandidateId = commitment`, actor `ai`) → postconditions against the grant's **expected revision after** → committed → adopted → receipt (`sirkit.agent-execution-receipt.v1`, approval actor `human:confirmed-preview` | `server-grant:execute_explicit`) → autosave → SETTLE from the receipt. Post-consume failures settle `not-committed` (nothing landed) or `poisoned` (a landed commit that cannot be verified) — poisoning always sends the `poisoned` report too, inline and in the sweep. A lost tender ANSWER (transport failure twice) keeps the prepared entry for the sweep because the server may hold the consumption. An explicit grant refused before the consume (foreign scope, superseded lifecycle, missing session, recompile mismatch, journal unavailable) is cancelled durably so the awaiting run is answered at once; preview grants are left for the human. Replays never double-commit (memory, then journal + canonical evidence, then the executor's own idempotency). The journal's terminal state is `settled` (the server holds the report): a committed execution whose settle exchange failed stays `receipt-finalized` and the sweep re-sends the report from the receipt (late when the window elapsed). The hydration sweep finishes crashed attempts from the journal entry alone (adopt proven commits and settle them; re-settle finalized entries; abandon consumed-but-uncommitted entries after the commit window; poison — and report poisoned — claims the ledger cannot prove; a journal write failure during adoption never poisons a proven commit). The editor scopes the journal by the lineage ROOT board id (the identity the grant is minted and checked against), settles a pending grant BY ID, and cancels durably when the lifecycle moves under a pending grant or an explicit grant fails its live pre-check.

Measured on the real composition: one transaction with actor `ai` and `provenance.candidateId = commitment`; the server record settled `committed` with the transaction id and the awaiting minter resolved from it; the preview Confirm path; replays from memory and from journal + evidence with the head unchanged; drift refused with durable cancellation; forgeries, expiry, foreign scope and session-less grants refused before any exchange; a refused consume (session changed) with the grant retired and the entry abandoned; a lifecycle retirement after the consume settled `not-committed`; three crash recoveries.

## 7. Unforgeability (INFERRED from the enforced mechanisms above)

Server-side storage of the record + nonce; the binding to the verified principal, session identity and membership revision at mint and again at consume; single use by compare-and-set; the canonical wrappers on every route; the explicit-request proof by derivation; the browser's chain-protected commitment in the hash-chained canonical ledger. A grant received by any party other than the bound principal in the bound session is a 404 with zero writes.

## 8. Recorded observations (RECORDED)

- R18-1: the wrapper's exact-origin check is production-only (B16.0.1 design); this environment's unconfigured production identity refuses cross-origin POSTs earlier (`AUTH_PRODUCTION_NOT_CONFIGURED`) — the route test asserts 403 with zero store access and leaves the origin semantics to the B16.0.1/0.2 CSRF suites.
- R18-2: the staged-content secret scan matched `private key(` (a `private` class method named `key` in the journal source) during the B7 push — a false positive of the case-insensitive `PRIVATE KEY` pattern; the chain echoed the hit without aborting and the push proceeded. No credential material was involved. The scan now uses the PEM marker `-----BEGIN … PRIVATE KEY-----` and aborts on a hit.
- R18-3: two test-authoring defects were fixed while proving the ritual (the journal's re-seal hashed the stale checksum into the body; the retry guard counted a not-committed settlement as an execution) — both are product fixes, recorded in `ada258d`.
- R18-4: no scripted LLM adapter exists for browser runs (discovery); the browser proof of the grant ritual is the real-composition suite above and the B18-E scenarios will drive the page's receivers directly, as B17-F did.
- R18-5 (adversarial review, 15 agents, 2026-09-10): six lenses produced 30 raw / 25 unique findings; 9 verified by refutation → 7 confirmed (5 distinct), 2 refuted; 16 were not verified in that pass and were read by hand — 13 of them were fixed as real (poisoned reporting, expiry gate, zero-write forgeries incl. lazy expiry, mint replay, late reports, boundary retirement, journal scope by root board id, settle-failed re-settlement, poisoned reports from the sweep, lost tender answers, explicit pre-consume cancellation, settlement by grant id, activity-log status, the exact membership burn reason), 3 recorded without a change (R18-6/7/8).
- R18-6: recovery adopts a proven commit with the grant's PINNED expected revision after (the compiled result of the pinned operations from the pinned base) rather than a re-derived one; the commitment + single head advance prove the transaction is the grant's own. INFERRED sufficient; a live-board re-check is only possible while the head is exactly base + 1.
- R18-7: the run trace records the grant at issue (class `execution_grant`, identity + operations digest) but does not mirror the settlement the model was told; adding a trace event kind is a B18-C item (the trace vocabulary is pinned by B11).
- R18-8: the execution single-flight is keyed on the descriptor class before invocation and on the outcome after it; until B18-C exposes a mutate-class tool the pre-invocation branch is unexercised by tests (RECORDED).
